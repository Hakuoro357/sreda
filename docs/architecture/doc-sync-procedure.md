# Процедура doc-sync на закрытии задачи (анти doc-drift)

**Owner:** vex-assistant#248
**Это процедура оркестратора (агента), не рантайм-код.** Тулинг — `scripts/affected_docs.py`,
`scripts/docs_registry.py`, `scripts/check_docs_freshness.py`. Правило-крючок — в глобальном
ПРАВИЛЕ #7 (приёмка). Активируется там, где у проекта есть enrolled-доки (поле `Verified-against`).

## Зачем

Реактивный слой (`check_docs_freshness.py` + красный `main`) ловит дрейф ПОСТФАКТУМ. Эта процедура —
проактивный слой: на закрытии задачи синкает задетые доки с кодом, чтобы дрейф не появился, и бампает
`Verified-against` — тогда свежесть зеленеет по правильной причине, а не от пустого штампа.

## Триггер 1 — планирование (в чеклист приёмки)

При черновике чеклиста приёмки (ПРАВИЛО #7) запустить определитель на предполагаемый набор файлов:

    python scripts/affected_docs.py --files <предполагаемые файлы>

На каждый задетый док добавить пункт приёмки:
«док D сверён с кодом + `Verified-against` бампнут на HEAD закрытия + Haiku-verify PASS».
Так обновление дока — ожидаемый пункт, а не сюрприз на закрытии.

## Триггер 2 — закрытие задачи

    python scripts/affected_docs.py --range origin/main...HEAD

Пусто → **no-op** (задача не трогала enrolled-источники, синк не нужен). Иначе на каждый док:

### Шаг 1. Sync-агент (правит док)
- **Вход:** текущий код файлов `Source code` (читать ЦЕЛИКОМ — это ИСТОЧНИК ИСТИНЫ), диф задачи
  (только навигация — что и почему менялось), текущий док, issue (намерение/именование).
- **Поведение — claim-by-claim против ТЕКУЩЕГО кода:**
  - **ADD** — поведение есть в коде, нет в доке;
  - **UPDATE** — утверждение дока, чей код изменился (напр. изменился дефолт флага);
  - **авто-DELETE** — ТОЛЬКО символ (функция/флаг/поле), которого нет **во всём текущем коде-источнике**
    (не «исчез из хунка дифа» — иначе переименование читается как удаление);
  - **FLAG (⚠, не молча)** — сомнительные удаления (переформулировки, абзацы-обоснования, инварианты
    «на глаз») И сигнал по смежному коду (soft из определителя): смежный файл — не отслеживаемый
    источник истины, по нему НЕ правим, только помечаем «проверь вручную».
  - Каждое оставленное/добавленное утверждение — со ссылкой на символ кода (как в ПРАВИЛЕ #7 «цитируй»).
- **Выход:** предложенный дифф дока + бамп `Verified-against` на HEAD + заметка
  `{added, updated, auto_deleted, flagged}`. НЕ применяется до verify и взгляда владельца.

### Шаг 2. Verify-агент (независимая проверка) — Haiku, ОТДЕЛЬНЫЙ вызов
- **Вход — ТОЛЬКО:** синканый док + текущий код источников. НЕ давать диф, заметку sync-агента, issue —
  иначе это самосертификация (дыра ПРАВИЛА #7, прецедент #74). Независимость = весь смысл прохода.
- **Проверяет:** каждое конкретное утверждение дока (сигнатура, дефолт флага, перечень доменов, ветка
  политики) подтверждено текущим кодом; нет осиротевших утверждений (код удалён). Не судит полноту
  исчерпывающе (это взгляд владельца + ADD-проход).
- **Выход:** `PASS` / список несоответствий `{утверждение, что говорит код, вердикт}`.
- **Эскалация модели:** крупный/поведенчески-плотный док (суммарно док+источники не влезают в окно Haiku,
  или раздел — тонкая поведенческая политика) → verify на Sonnet. Порог по суммарному размеру — настроить
  по факту.

### Шаг 3. Петля и эскалация
- Verify FAIL → вернуть sync-агенту конкретные несоответствия. **Потолок 2 раунда sync↔verify.**
- Не сошлось за 2 → СТОП, не применять, вынести остаток владельцу как ⚠-блок.

### Шаг 4. Взгляд владельца (на приёмке)
- Владелец смотрит дифф дока, ОСОБЕННО ⚠-flagged-блок и авто-удаления.
- На «ок» — применяем (с бампом `Verified-against`). `check_docs_freshness.py` зеленеет по делу.

## Честная рамка (не гарантия)

Это ДЕТЕКЦИЯ, не гарантия (как и сам ПРАВИЛО #7). Главный риск — sync-агент заносит НОВУЮ ошибку в док,
а зелёная свежесть её «узаконивает». Сдерживание: источник истины = текущий код (не диф), консервативное
удаление, отдельный Haiku-verify, взгляд владельца. Взгляд владельца — настоящая подстраховка; Haiku —
дешёвый независимый фильтр механических несоответствий до владельца. Зелёная свежесть сертифицирует
«кто-то сверил с кодом», НЕ «док доказанно верен».

## Инструментация (по желанию)

Лёгкий лог счётчиков на прогон: `auto_deleted` / `flagged` / `owner_overruled` — чтобы судить о пользе
механизма. Высокая доля flagged/overruled → механизм нетто-отрицателен, пересмотреть.
