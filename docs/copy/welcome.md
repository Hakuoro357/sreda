# Копирайт: приветственные реплики

Документ описывает ВСЕ welcome-сценарии, которые бот отправляет новому
или approved-юзеру. Это индекс для команды; точные тексты живут в
кодовых константах, указанных ниже.

Каждый текст сопровождается:
- цитатой (как видит юзер)
- триггером (когда отправляется)
- кнопками (если есть)
- местом в коде (файл:функция)

---

## 0. Контекст

Новый пользователь присылает `/start`. В БД создаётся `Tenant` с
`approved_at = NULL` («pending approval»). Админ должен вручную
нажать «Одобрить» в `/admin/users` — это «костыль до запуска
подписок» (защита от массового набега).

Юзер в pending-фазе получает **pending-bot** (scripted, без LLM).
С 2026-05-22 это **цепочка из 5 коротких сообщений** —
intro + voice + routine + memory/search + pending-closing.
В approved persona-tour финальный экран заменяется вопросом имени.

История версий:
* 2026-04-25: 7 веток демо-рассказа с кнопками-темами.
* 2026-04-27 (утро): упрощено до одного длинного welcome без кнопок.
* 2026-04-27 (вечер): разбито обратно на 10 коротких — длинная
  портянка плохо читалась в Telegram.
* 2026-04-29: 11-step tour (добавлены schedule/reminders/dont_do).
* 2026-05-08: сокращено 11 → 4. Drop-off ~50% к 6-му тапу. Старые
  ветки aliased на intro для backwards-compat in-progress туров.
* 2026-05-22: обновлено под persona onboarding и текущие возможности:
  5 экранов, отдельный блок бытовой рутины, без privacy/disclaimer
  портянки; approved-вариант финала спрашивает имя.

После выбора личности пользователь может открыть tour с примерами или
сразу перейти к обычному диалогу. В approved-варианте tour финальный
экран спрашивает имя.

**Ключевые принципы тона** (не обсуждается, прошито в prompt + тестах):

1. **Анти-сталкер.** Не пишем первыми без повода, не считаем вслух
   упоминания, при запросе данных объясняем «зачем».
2. **Gender-neutral к юзеру.** Никакого прошедшего времени в
   ж.р. («ты сказала», «ты сама», «ты попросила»). Допустимы
   безличные формы или скобочные `(-а)`. Про Среду ж.р. разрешён.
3. **«Ты» форма** во всех текстах без исключений.
4. **Кнопки** на каждый вопрос. «Да / Нет» запрещены — только
   конкретные реплики («Да, собери меню», «Не сейчас»).
5. **Цены — плейсхолдеры** из БД через `services/pricing.py`.
6. **Без Markdown.** Telegram не рендерит `**жирный**`.
7. **Без технических терминов.** Никаких «агент», «Mini App»,
   «лимит тарифа», «хронические лекарства».

## 1. Pending welcome / tour (цепочка из 5 сообщений)

**Триггер.** Любое входящее от юзера в pending-фазе:
- `/start` от непрошедшего approval юзера (`tenant.approved_at IS NULL`)
- любой text-message
- любое голосовое (без STT — pending-фаза не тратит Groq/Yandex)
- любой callback (включая устаревшие `pb:<branch>` от прошлых версий —
  fallback'ятся в intro)

**Файл.** `src/sreda/services/pending_bot.py`

**Поток.** Каждое сообщение, кроме финального, содержит ровно одну
кнопку «следующая тема →». Юзер тапает → приходит следующее
сообщение. Если юзер пропустит шаг и напишет text — вернётся в intro.
Wizard-style: одно сообщение в чате, текст эволюционирует через
`editMessageText`.

| # | branch_key | Кнопка ведёт на | Тема |
|---|---|---|---|
| 1 | `intro` | `🎙️ Голос →` | Коротко: какие задачи закрывает |
| 2 | `voice` | `🏠 Бытовая рутина →` | Голос как основной режим работы |
| 3 | `routine` | `🧠 Память и поиск →` | Напоминания, покупки, чек-листы, меню, рецепты |
| 4 | `memory` | `Готово ✓` | Семья, факты, погода, интернет |
| 5 | `done` | — (нет кнопок) | Pending-closing до одобрения |

**Тексты сообщений** — см. константы `_INTRO`, `_VOICE`, `_MEMORY`,
`_DONE`, `_DONE_BROADCAST` в `pending_bot.py`. Никаких внешних
копий — изменения текста делаются ТАМ, этот документ — индекс.

**Замечания:**
- Голос (`voice`) — первое подробное сообщение после intro: голос
  основной режим работы со Средой, а не «ещё одна возможность».
- Privacy/disclaimer портянка удалена из тура. Первый опыт должен
  показывать пользу, а не список ограничений.
- Для approved persona-tour используется тот же wizard, но финальный
  текст заменяется на вопрос «Как мне к тебе обращаться?». Следующий
  текст deterministic сохраняется как `TenantUserProfile.display_name`,
  затем бот отвечает без кнопок: «Запомнила... Есть вопросы ко мне?
  Или начнём сразу — что будем делать первым?»

**Aliases для backwards-compat.** Устаревшие callback_data из
прошлых версий маршрутизируются в `intro`:
- Pre-edit-wizard эра: `pb:welcome`, `pb:what`, `pb:demo_morning`,
  `pb:menu_example`, `pb:life`.
- 2026-04-29 11-step tour (сокращён 2026-05-08): `pb:schedule`,
  `pb:reminders`, `pb:checklists`, `pb:shopping`, `pb:recipes`,
  `pb:family`, `pb:dont_do`.

In-progress tours с `last_branch="schedule"` etc. в БД продолжают
работать — следующий тап загружает `_INTRO` reply, новый wizard
flow с 5 шагами.

## 2. Persona onboarding / approved user flow

**Триггер.** Approved user просит настройки личности или получает
onboarding после включения доступа.

**Файлы.**
- `src/sreda/services/housewife_persona.py`
- `src/sreda/services/housewife_onboarding.py`
- `src/sreda/services/telegram_bot.py`
- `src/sreda/services/max_inbound.py`

**Первое сообщение:**
```
Я Среда — AI помощница для семьи!

Помогаю с бытовой рутиной:
• 🎙 понимаю голос — можно просто поговорить со мной;
• ⏰ ставлю напоминания и задачи в расписание;
• 🛒 веду список покупок и отмечаю купленное;
• 📋 веду чек-листы дел;
• 🍽 составляю меню на неделю и собираю продукты к нему;
• 📖 сохраняю и нахожу рецепты;
• 👨‍👩‍👧 запоминаю важное про семью: состав, привычки, диеты, аллергии;
• 🧠 помню факты, события и договоренности;
• 🌤 могу подсказать погоду;
• 🔍 ищу в интернете факты, новости, расписания и адреса.

Выбери, как мне с тобой общаться:
```

**Кнопки.**
- `Спокойно и по делу` → `persona:warm_practical`
- `Ласково и тепло` → `persona:tender_care`

После выбора личности бот редактирует то же сообщение:
```
Выбрала <стиль>.

Дальше можно сразу дать мне задачу — текстом или голосом.
А можно сначала посмотреть пару примеров, чем я могу помочь.
```

**Кнопки.**
- `Покажи примеры` → `pb:intro`
- `Давай сразу` → `persona_ready`

Если пользователь проходит tour до `pb:done`, следующий текст
детерминированно сохраняется как `TenantUserProfile.display_name`.
Ответ после сохранения:
```
Запомнила, буду обращаться к тебе: {name}.

Есть вопросы ко мне?
Или начнём сразу — что будем делать первым?
```

Кнопок в этом сообщении нет: дальше начинается обычный диалог.

**Замечания.**
- Выбор личности глобальный для пользователя и синхронизируется между
  TG/MAX linked channels.
- Имя после `pb:done` не отправляется в LLM, чтобы не получить
  произвольное summary вместо имени.
- Старый post-approval flow через `build_post_approve_message` остаётся
  для совместимости, но продуктовый onboarding идёт через persona flow.

**Sanitizer для display_name (2026-04-28 incident).** На проде
обнаружили 3 испорченных `display_name` — LLM передавала в
`onboarding_answered.summary` целые фразы вместо имени:
- `"Пользователя зовут Борис."`
- `"Пользователь хочет, чтобы его называли «Шеф»."`
- `"Пользователя зовут Повелитель — просил называть его так."`

Защита трёхслойная (см. `services/housewife_onboarding._extract_short_name`):
1. **Tool docstring** в `services/housewife_chat_tools.onboarding_answered` —
   явные ПРАВИЛЬНО / ЗАПРЕЩЕНО примеры.
2. **Prompt rule №5** в `format_for_prompt` — расширен с примерами
   запрещённых summary.
3. **Backend sanitizer** `_extract_short_name` — последняя линия
   обороны: режет префиксы «Пользователя зовут», «Меня зовут»,
   «Пользователь хочет, чтобы его называли», обрезает кавычки и
   терминальную пунктуацию, оставляет только первую часть до
   тире/запятой/точки. Применяется в `_set_display_name`
   (housewife) и в `runtime.handlers._validate_proposed_field`.

Существующие 3 испорченных значения исправлены вручную SQL UPDATE'ом
в проде:
- `tup_4da5c5567362487da11a22e7` (`tg_352612382`) → «Борис»
- `tup_d05ba443080c491694cd47f5` (`tg_30223042`) → «Повелитель»
- `tup_482305551f564a979e90b1b5` (`tg_981993906`) → «Шеф»
