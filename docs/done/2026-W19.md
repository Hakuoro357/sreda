2. `_HOUSEWIFE_FOOD_PROMPT` строка 994 (housewife addon с 2026-04-22):
   "Не отчитывайся о несделанном. Если говоришь user'у «сохранил 3

   tool-call..."

3. `_TOOL_DISCIPLINE_ADDENDUM` строка 1201 (всегда добавляется,
   с 2026-04-29):
   "ЗАПРЕЩЕНО говорить пользователю «Готово», «Поставила», «Создала»,
   «Добавила», «Напомню», «Будет напоминание» — если в ЭТОМ ЖЕ turn'е

**Проблема:**

- Три разных формулировки одного концепта
- Список запрещённых слов **не пересекается полностью** между правилами
  (CORE: Готово/Сделала/Настроила/Запомнила; ADDENDUM: Готово/
  Поставила/Создала/Добавила/Напомню/Будет напоминание; HOUSEWIFE:
  «сохранил X рецептов» паттерн)
- Если разработчик обновит ОДНО — остальные могут остаться stale
- LLM получает три overlapping инструкции — confusion vector

**Stage 1.1 НЕ создал эту проблему — она была до. Но Stage 1.1 её
усугубил** (третий слой).

**Fix (Stage 1.3, ~1 час):**

a) Объединить три rule'а в **одну canonical** в
   `_TOOL_DISCIPLINE_ADDENDUM` (он всегда грузится, имеет жёсткое
   ЗАПРЕЩЕНО формулировку).
b) Расширить список слов: объединение всех трёх (Готово, Сделала,
   Настроила, Запомнила, Поставила, Создала, Добавила, Напомню,
   Будет напоминание).
c) Убрать дубль из `_CORE_SYSTEM_PROMPT` (line 961, добавлено в Stage 1.1).
d) Убрать дубль из `_HOUSEWIFE_FOOD_PROMPT` (line 994).
e) Обновить `test_anti_confabulation_prompt.py` — проверять
   правило в `_TOOL_DISCIPLINE_ADDENDUM` (через regex или
   `build_system_prompt(None)` с предположением что ADDENDUM в ней).
f) **Сохранить Stage 1.1 capability-rule** (line 962, про
   log_unsupported_request) — он уникальный, не дублируется.

**Risks:**
- Низкие. Правила семантически эквивалентны, объединение не меняет
  поведение LLM. Есть 4 lock-in теста + smoke checklist.
- Side effect: вместо трёх «слабых сигналов» одна «сильная инструкция»
  — теоретически можно даже улучшить compliance.

**Когда:** P3, не блокер. Делать когда придётся снова трогать
любое из трёх правил — тогда консолидировать в одной транзакции.

### 13.2. Embedding endpoint — ✅ DONE (root cause fix)

**Найдено утром.** `recall_memory` молча возвращал `[]` всем юзерам с момента
SQLite→PG миграции (~05-01). `/etc/sreda/.env` потерял `SREDA_EMBEDDINGS_*`,
fallback на `FakeEmbeddingClient(dim=64)` против хранимых 1024-dim → cos=0.0
→ всё фильтруется ниже min_score → бот честно говорит «нет в памяти».

**Зашли:**
1. Сначала e5-large через neuraldeep.ru (free tier, 250/h лимит).
2. Re-embed 6 битых dim=64 записей (Boris адрес, Марина Стамбул, Юлечкин
   tz×2 + обращение, Катин брат др).
3. Подтверждено что recall работает: scores 0.71-0.78, `seeded=10`.

**Затем переключились на bge-m3 через cloud.ru** (Foundation Models, pay-as-you-go,
200 RPS, 0.61 ₽/1M токенов). Вердикт лучше: больше gap relevant/irrelevant
(0.42-0.48 vs 0.25-0.44 у Qwen3-Embedding-0.6B), нет жёстких rate-limits.
Re-embed всех 261 записи (50 memories + 66 checklist + 145 reminders) за 1 мин 22 сек.

**Файлы:**
- `services/embeddings.py` — `EMBEDDING_MODEL_NAME = "bge-m3"`
- `scripts/reembed_all_with_current_model.py` (новый) — для будущих model swap'ов
- `scripts/backfill_structured_embeddings.py` — uses cloud.ru bge-m3
- prod env: `SREDA_EMBEDDINGS_BASE_URL=https://foundation-models.api.cloud.ru/v1`

**Lessons (для plan-mistakes):**
- Settings без default'а → silent fallback на fake клиент = months-long bug. Добавить
  startup-time check: «если `embeddings_model is None` — log critical».
- Fixed-window rate-limits (250/h на neuraldeep): backfill попадает в шум активного
  траффика. Pay-as-you-go (cloud.ru 200 RPS) предпочтительнее для prod.
- Embedding model swap = re-embed ВСЕЙ базы (vector spaces несовместимы, cos=0.04
  на same text между bge-m3 и qwen3-emb). Скрипт должен быть idempotent.
